## 四 · ★ 可追溯:窗口 / 池子 / 阈值原文

### 窗口
用的是 **2018-01-01 .. 2025-12-31**,2,011 个交易日。
★ 任务单提到 `probe/fundamental_buildout_1030/` 那一轮的 2018-01-01 ~ 2020-12-31,
但 **`gate_decomposition()` 当轮用的不是它** —— 它用的是 `engine/data.py` 的
`PERF_START = "2018-01-01"` / `PERF_END = "2025-12-31"`(见 `run_masters_57_1030.py` 里
`perf = (cal >= PERF_START) & (cal <= PERF_END)`)。按任务单「以它的为准」,本轮照 8 年窗口跑,
并已核对:老库四个数和 1030 的结果文件逐位一致,证明窗口对上了。

### 池子口径
`engine/pool_scope.py`:`DEFAULT_SCOPE = "large_mid"`,`SCOPES["large_mid"] = (1, 2000)`,
筛选判据实际源码:

```python
def in_scope(rank, scope=None):
    lo, hi = SCOPES[active_scope(scope)]
    return rank is not None and rank >= lo and (hi is None or rank <= hi)
```

池子文件 `probe/survivorship_1029/pool_FULL_ALL.csv`(74,268 行,只读)。
实测 2018–2025 每年 rank ≤ 2000 的公司数都是 **2,000**,去重后 company_id 也是 2,000 —— 没有重复行。

### 闸门阈值(★ 逐字抄自 `engine/configs/quality_compounder.yaml` ① 段,一个都没改)

```yaml
    - type: roic_consecutive_above
      params: { years: 3, min_roic_pct: 15.0, basis: TTM }
      source: 行业基于 Dorsey 思想的量化改写版

    - type: gross_profit_to_assets_rank_above
      params: { min_percentile: 80.0, basis: TTM }
      source: 行业惯例

    - type: net_debt_to_ebitda_below
      params: { threshold: 2.5, basis: TTM }
      source: 行业惯例
```

### PIT
`engine/fundamentals.py`,原封不动复用,四条铁律都在:
申报日 **+1 个交易日**才生效(`effective_date()`)· 流量科目 **YTD 差分还原单季**再滚 TTM ·
TTM 要求 **四季时间连续**(相邻期末相隔 70–120 天),缺一季不给数 · 同一期**只留首发版本**,不用重述。
日频铺开用 `_to_daily()`:生效日起可见,未公布期间 ffill,首次公布前 NaN(= 那天算不出)。

### 指标算法
`probe/masters_57_1030/ops_q57_1030.py:metric_q()`,**原封不动调用**,没有另写一份:
- ROIC = `EBIT×(1−税率) / (有息负债+股东权益−现金)`,税率 = `(IncomeBeforeTax−NetIncome)/IncomeBeforeTax` 且必须落在 [0,1];有息负债 = `LongTermDebt+ShortTermBorrowings+LongTermDebtCurrent`(三个全缺 = NaN,不按 0 算)
- 净负债÷EBITDA:EBITDA = `EBIT + D&A`(D&A 两种标签都认);**EBITDA ≤ 0 判不合格**,不判「杠杆低」
- GP/A = `(Revenue − CostOfRevenue) / TotalAssets`,再做**池内横截面** `rank(pct=True) ≥ 0.80`

### engine 改动
**零。** 新库的 `.json.gz` 是在本轮脚本里**运行时把 `data.load_fundamentals` 这个函数引用换掉**读的
(`use_ext_library()`),`engine/data.py` 文件本身一个字符都没动,`load_fundamentals()` 仍然只认 `.json`。

## 附录 B · 口径上必须留痕的三件事

1. **③ 的横截面分位是在「脚本列集合」里排的,不是在「当天在池的那批」里排的。**
   `gp.rank(axis=1, pct=True)` 对整张表的列做排名 —— 1030 那一轮也是这么做的(照抄),
   但新库的列集合是 3,031 只(跨年并集),比任一天在池的 ~1,850 只大。
   ★ 后果:算不出的票不参与排名,所以「前 20%」实际是「**算得出的那批里**的前 20%」,
   这道闸比纸面上松;列集合变大会让它再松一点。★ 本轮没改它,因为改了就和老库不可比。
2. **新库的 EBIT 和老库一样是推导值**(`derived_from_sec_pit_facts`,`IncomeBeforeTax + InterestExpense`)。
   ★ `quality_compounder.yaml` 里写着「已否决的替代:EBIT ≈ 税前利润 + 利息费用」——
   但老库里的 EBIT 本来就是这么来的(实测 250 只共 14,100 条 EBIT 记录,**100%** 是这个 source_type),
   所以这不是本轮引入的新口径问题,是一条**早就存在、两库共有**的事实。★ 要不要翻这个否决,是策略层面的事,不在本轮。
3. **本轮只量了 ① 选股范围这一步。** ② 环境过滤(SPY/VIX)、③ 进场扳机、④ 止损宽度一个都没跑。
   所以「6.7 只/天」是**基本面候选池**的只数,不是成交笔数。
