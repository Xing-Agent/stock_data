## 1  这个 Skill 管什么

帮用户配置 agent:选方法、设参数、定提醒规则。

## 2  什么时候用

★ 用户原话（★★ 共同特征：**他说的里面有一个具体标的**）：

- 「帮我盯一下 **NVDA** 跌破 20 日均线」
- 「帮我盯着这个条件，到了告诉我」
- 「我想把这套做法固定下来，用在 **AMD** 上」
- 「用温斯坦那套盯着 **MSFT**」
- ★★ 「上个月那个 agent 我想改一下参数」

★★★ **分流判据（★ 唯一一条机械判据）：有标的 → 这张卡；没标的 → `xing-skill-builder`。**

## 3  不管什么,交给谁

- 替他选方法 → 不管,那是他的决定
- 评价某只股票 → **行情 / K线互动**
- 让他定义全新的规则 → **创建技能**

## 4  这个场景属于哪一档

**搭工具。主动 —— 该给建议就给,而且应该给。**

在一个设置参数的界面上还说「这个判断是你的」,那不是克制,是不帮忙。
**但建议的是「这个参数怎么填」,不是「这只股票该不该买」。**

## 6  这个 Skill 特有的禁令

**一、两套参数值并列,默认原著值。**
原著值 + 我们校准的推荐值,讲清两者的特点和测法,**不推荐哪个**。
默认原著值 —— 用户没主动选之前,不该让他绑在我们自己的规则上。

**二、从原著值切到推荐值,要用户点一下。那一下才是授权。**

**三、绑定之前必须把代价摆出来,不能藏在二级页面。**

七个数 + 可执行率。其中两个的说法已经定了:

> **最大连亏**不能只说「最大连亏 27」,要说
> **「你要准备好连着错 27 次,而且它们会挤在一起来。」**

> **最长水下**不能只说「18 个月」,要说清它包含空仓干等的时间 ——
> 用户的体感是「我账户里的数,18 个月没比之前的最高点更高过」。

★★★ **四、并列展示多个策略时：按流派分组，组内才排序。**（★ 2026-11-03 定）

```
★★★ 为什么必须按流派分组:**跨流派比胜率是有害的。**
   ★ 突破类赌的是「波动率瞬间扩张」→ **低胜率、极高赔率**;
   ★★ 均值回归赌的是「钟摆会回摆」→ **高胜率、低赔率**。
   ★★★ 拿突破的胜率去和均值回归的胜率排序,
      **会把突破永远排在后面** —— ★ 而那不是它差,**是它本来就长那样**。

★★ 分组的样子:

   ── 突破类 ────────────────────────
      技-3 温斯坦      止损宽度 10.9%   一年约 × 次
      技-5 VCP        止损宽度 4.2%    一年约 × 次
   ── 均值回归类 ─────────────────────
      技-14 布林带     止损宽度 2.0%    一年约 × 次
      技-10 海龟汤     止损宽度 3.8%    一年约 × 次

★★★ 两条硬要求:
   ★★★ ① **组内可以排序,跨组不许排。**
   ★★★ ② **组与组之间不许出现任何「哪一组更好」的暗示** ——
      ★ 包括顺序(★★ 所以组的顺序按**字母或固定顺序**,不按表现)。
★★ 而「**同一流派内部的代价数字才可比**」这句话,
   ★ 要**写在分组的表头上** —— ★★★ 不写,用户会跨组比。
```

★★★ **还有一条和它绑着的（★ 重叠预警）：**

```
★ 实测:我们的**四对**方法两边重叠(★★ 涉及 6 套打法里的四套):
   技-5 VCP ↔ 龙头动量 · 技-1 趋势跟随 ↔ 趋势跟随打法 ·
   技-10 海龟汤 ↔ 流动性猎杀 · 基-9 困境深度价值 ↔ 深度价值打法
★★★ 他**同时选了两个**底层一样的,才弹一句:
   「⚠ 你选的「龙头动量打法」底层**已经包含**「技-5 VCP」的全部核心逻辑。
     两者历史收益相关性 ××。
     ★★★ **同时跑会让风险暴露翻倍,而不会分散。**」
★★ **只在真的会出事的时候才出现,平时不占屏幕。**
   ★ 相关性是我们自己算得出来的。
```

**五、自研策略严禁套用大师的名字。**
一条我们测出来的规则挂上大师名字,对用户是误导(他以为有几十年验证)。

## 6附  和「创建技能」的分工 —— 两个 Skill,一个入口

**不合并。**理由不是用户认知,是**生命周期不同:**

| | 是什么 | 改了之后影响谁 |
|---|---|---|
| **技能** | **可复用的定义** —— 做一次,到处用 | 所有用它的 agent |
| **agent** | **运行中的实例** —— 挂着标的、有状态、会提醒 | 只有它自己 |

合并等于把「菜谱」和「正在炖的那锅汤」合并。**用户改菜谱的时候,正在炖的那锅怎么办?**
那个问题在合并后的架构里无解。

### 分流判据:他说的里面有没有具体标的

| 用户说 | 判据 | 去哪 |
|---|---|---|
| 「帮我盯一下 **NVDA** 跌破 20 日均线」 | **有标的** → 要的是实例 | **这个 Skill** |
| 「我想做个筛选,找**所有**跌破 20 日均线的」 | **没标的** → 要的是规则 | **创建技能** |

**用户永远不需要知道「agent」和「技能」这两个词。**入口统一,底下分流。

### 引导不在入口,在他重复第三次的时候

**入口不要问「你要建 agent 还是技能」** —— 他不知道,问了也是猜。

```
第一次  「帮我盯 NVDA 跌破 20 日均线」   → 建 agent
第二次  「AMD 也帮我盯一下」             → 再建一个
第三次  「META 也是」
          ↓
系统主动说:「这个条件你用了三次了。要不要存成你自己的技能?
            存了之后下次直接挂标的就行,不用每次重设。」
```

**在他自己已经证明了需求之后再提。**这样他一定懂,因为他刚做了三遍。

### 编辑时必须说出后果

| 场景 | 系统要说什么 |
|---|---|
| 用户改一个**被多个 agent 用着的技能** | **「这会同时影响正在跑的 3 个 agent。改这一个还是全部?」** |
| 用户在 agent 里改的是**条件本身** | 「你改的是技能的定义。只对这个 agent 生效,还是改技能本身?」 |

**那个「菜谱 vs 正在炖的汤」的问题,在这里变成一句用户听得懂的话。**

## 绑定规则前的前置条件

本技能创建的观察任务若绑定某条规则，该规则必须已完成 `xing-skill-builder`
「验证的四样底线」全部四项（样本外区间、系统随机对照组、参数脆弱度与起点敏感度、
调参次数计数器），且四项结果可随任务一并查看。

未完成的规则可以绑定为草稿任务，但不得标记为已验证，也不得据此推送交易提示。

## 「做不了」的时候，必须同时说出能给什么（2026-11-10 · Lin 定：结构那半进 V3，这半 V2 先做）

用户要「盯盘 / 到价提醒 / 定时扫描」这类事时，**做不了的要说清，能给的也要说出来**。

**做不了的（这几件现在真没有，不要含糊，也不要暗示将来一定有）**
- 条件引擎（到价自动提醒）—— 没做，所以**一个「会提醒你」都不许出现**
- 主动推送 · 全池扫描 · 定时任务

**能给的（这三样现在就有，不许一个都不提）**
1. **平台「我的专家 → 创建专家」** —— 用户可以把这套规则固化成一个自己的专家：
   输入专家名称与指令、选择可用技能、保存。
   这个功能**确实存在**，本卡前文已写明「不得再说平台不能创建专家」。
2. **规则草稿** —— 把用户那句话整理成「范围 / 条件 / 频率」三段，现在就能给。
3. **用户自己那端的提醒** —— 到价提醒可以先在他的券商端设。

说完「做不了」就停住，是把用户往外推 —— 而东西就在我们手里。

**这一版的局限（写在这里，免得下一轮又当新发现）**：
上面是一张**固定清单**，只覆盖盯盘这一类。换成别的场景（例如「几号见顶」），
清单管不到，还是可能只说一句「做不了」。要根上解决，需要把「能给什么」做成
**输出里不许为空的一格**，机器才查得出来 —— 那是 V3 的事。
