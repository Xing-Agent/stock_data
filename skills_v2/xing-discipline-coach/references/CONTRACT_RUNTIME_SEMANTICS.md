# 契约运行规则（v5 → v3 工程落地）

- `draft` 可包含缺失的评估字段；`user_confirmed` 必须有不可伪造的 `user_approval`，没有真实后端事件不能改为确认态。
- 条件类型只含 `price/financial/event/time`。任意有效启用条件都必须明确：比较运算符、阈值、观察频率、触发时点、持续期、过期/复位、数据来源、缺失状态、通知方式；自然语言解释不能代替代码级评估器。
- `combination_mode=at_least_k_same_evaluation_time` 为一期唯一语义。只对 `enabled=true` 的 N 条条件求值；1 <= required_count <= N；满足 t 条、未知 u 条时：t>=k → TRIGGERED；t+u<k → NOT_TRIGGERED；其余 UNKNOWN。
- 用户关闭条件导致 N 改变，或改动 k/阈值/持续期/止损时，必须展示差异、由用户确认新版本；旧版本永久留存。尚未确认时原版仍有效，或明确暂停并告知，禁止自动调小 k。
- 数据过期/延迟/断源/停牌不能退为 FALSE；恢复后按原评估时点补算并记录补发。必须写入 market_timestamp、observed_at、evaluated_at、timezone、calendar、data_quality。
- 条件被触发不是通知已送达；通知不是自报；上传凭证不等于账户成交；券商 API 与导入文件都需查连续性、版本、标的、方向、数量、价格容差、执行时间窗。
- 组合条件频率差异明显且 k>1 时提示风险：同时满足可能很少，不能靠历史不触发断言未来永不触发。
- 原始规则、市场快照、费用/成交假设和用户改动理由为影子轨迹保留；初期只埋原始数据，不能事后捏造反事实计算。
- 非实盘已验证的策略不可作为默认买卖条件。用户自填规则只在合法权限内记录和机械检测，不等于投资适当性核验。

## v3.1 分层实现
状态一 **已确认计划**：真实用户确认过一份只读规则版本，允许缺少可机读的阈值，只能手动复盘。
状态二 **符合监控配置条件**：逐条检查字段 ID、单位、来源、数值/事件窗、时区、数据新鲜度及生效范围；通过 ≠ 已通知。
状态三 **正在监控**：独立用户授权 + 后端真实订阅确认 + 评估器与数据准备就绪。任何失效/过期/断供 => 降级，不再绿灯。
重要：`user_approval.version_hash` 与 `monitor_subscription.activation_actor` 是**字段声明**，不是独立的身份认证；后端应依真实会话授权、不可变事件日志、签名/审计记录判定，不信任模型提交的这些值。
