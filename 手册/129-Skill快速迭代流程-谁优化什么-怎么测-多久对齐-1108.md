## 一之二、★★★★★ 「谁测谁改」还是「统一由 Lin 改」？（★ Lin 1108 14:28 问的）

```
★★★ 建议：**谁测谁改 —— 但 Lin 守两道闸。**
★ 理由不是分工习惯，是算术：★★ 38 个 skill × 每轮若干处修改，
  ★★★ 全部过 Lin 一个人，他就是瓶颈；★ 而且会挤掉他**唯一不可替代**的那部分活（策略）。
```

| 改什么 | 谁改 | ★ 要不要过 Lin |
|---|---|---|
| ★ 话术、示例、引导语、常见问题 | 运营自己 | ★★ **不用** |
| ★ 流程、呈现、K 线交互、agent 编辑的操作细节 | 产品自己 | ★★ **不用** |
| ★ 前后端接口、字段、路由 | 技术自己 | ★★ **不用** |
| ★★★ **策略判据 / 阈值 / 进出场逻辑** | ★★★★★ **只有 Lin** | ★ 本来就是他 |
| ★★★ **对外口径措辞**（成绩怎么说、代价怎么说、风险怎么说） | 提交给 Lin 定 | ★★★ **要** |
| ★★★ **共用边界** | 一个指定的人统一改 | ★★★ **要**（★ 它牵动 28 个） |

```
★★★★★ 所以 Lin 的角色从「修改者」变成「**两道闸的守门人**」：
   ① 策略判据　② 对外口径
★ 其余一律自改自测 —— ★★ 这样并行度最高，★★★ 而且出问题能归因到人。
```

### ★★★ 那「大家各改各的，风格会不会散掉」怎么办

```
★ 不靠 Lin 逐条看，★★★ 靠**机器做一致性体检**（这正好是 AI 擅长、人最烦的那种活）：
   · 全部 38 个对照 `common_boundaries.md` 逐条查：有没有违反边界
   · 术语是否统一（同一个概念有没有三种叫法）
   · 有没有把内部标记 / 开发讨论 / 测试记录泄漏到用户可见处
   · 有没有人越界改了策略判据（★★★ 这一条最该机器查 —— 人容易看漏）
→ ★★ 每轮冻结后**自动跑一遍**，出一张「不一致清单」，★ 各自认领各自修。
★★★ 这样风格统一不靠 Lin 的眼睛，靠一份共用边界 + 一次机器体检。
```

## 二、怎么测（★ 三档，按改动大小选，不要每次都全量）

| 档 | 什么时候用 | 测什么 | ★ 大概工作量 |
|---|---|---|---|
| ★ **一档 · 冒烟** | 改了错别字、示例、措辞 | ★ 该 skill 能正常跑通 + 输出没有内部标记泄漏 | 几分钟 |
| ★★ **二档 · 单卡回归** | 改了某一个 skill 的内容 | ★★ **只测这一个**：它自己那组固定题 + 输出格式 + 边界 | 半小时内 |
| ★★★★★ **三档 · 全量** | ★★★ **动了共用边界**，或发新版本前 | ★ 全部 38 个跑一遍 | 半天 |

```
★★★★★ 为什么「动共用边界 = 全量」：★ 实测 **28 个 skill 引用同一份共用边界**，
   ★★ 而且各份 md5 完全一致（★ 这一点现在做得对，不要破坏它）。
→ ★★★ 改它一行，等于同时改了 28 个 skill。★ 这是唯一必须全量的情形。
★★ 反过来：**改单个 skill 不要触发全量** —— 那是现在工作量大的主因。
```

### 2.1 每个 skill 要有「自己那组固定题」（★ 这是省工作量的关键）

```
★ 做法：每个 skill 配 **5~10 道固定输入**，写死期望里必须出现/必须不出现什么。
★★ 改完只跑它自己那组 → ★★★ 从「每次重测 38 个」变成「每次测 1 个」。
★ 谁来建：★★ 运营和产品各自为自己负责的 skill 建，★★★ AI 帮忙生成初版，人确认。
★★ 一次性成本大约一天，★★★ 之后每一轮都省。
```

## 三之二、★★★★★ 怎么排才不返工（★ Lin 1108 14:27 点的那条 —— 周一主要就讲这一节）

```
★ Lin 的原话要点：「AI 测很快，★★ 但测完前端后端还要改；
   ★★★ 而且第一二轮问题多，后面边际效应越来越少。怎么搭配，保证大家不返工？」
★★ 这一条点中了上一版流程最弱的地方：★★★ 我把「修复」当成便宜的一步，**它才是瓶颈**。
```

### 3.2.1 ★★★ 第一件：**问题分两类，分两条路走**（★ 混在一起是返工的头号来源）

| 类 | 是什么 | 谁修 | 多久 | ★ 什么时候复验 |
|---|---|---|---|---|
| ★★ **A 类 · 文字层** | 话术、示例、边界提示、措辞、格式 | 运营 / 产品 | **分钟级** | ★★★ **当场改、当场复验**，不等下一轮 |
| ★★★ **B 类 · 代码层** | 前端呈现、后端接口、数据字段、路由 | 技术 | **小时~天级** | ★★★★★ **进开发队列，下一轮才验** |

```
★★★★★ 为什么必须分开：★ 把 B 类塞进同一轮，整轮就被最慢的那一条拖住；
   ★★ 而 A 类本来几分钟就能闭环。★★★ 现在的「测完要等很久」多半是被 B 类拖的。
★★ 做法：测试报告出来**第一件事是分流**，★ 报告里每条问题都要标 **A 还是 B**。
```

### 3.2.2 ★★★★★ 第二件：**按依赖顺序冻结**（★ 这是「不返工」的真正机关）

```
★ 依赖链（上游动一下，下游全部白测）：
    共用边界（28 个 skill 共用） → 两张大卡 → 25 张小卡 → 前后端接线
★★★ 所以冻结顺序必须**从上游往下游**：
    周一  ★★★★★ **共用边界先冻** —— 这一轮之内谁都不许动它
    周二  ★★ 两张大卡冻
    周三  ★ 小卡 + 接线冻（18:00 总冻结）
→ ★★★ 上游没冻就测下游 = **白测**。★ 今天这一类教训我们吃过：
   口径还在动的时候跑出来的数，最后全部作废重跑。
```

### 3.2.3 ★★★ 第三件：**轮次递减，并写死停止条件**（★ 对应 Lin 说的边际效应）

| 轮 | 测什么 | 预计发现 |
|---|---|---|
| ★★★ 第 1 轮 | **全量**（38 个） | ★ 最多 |
| ★★ 第 2 轮 | ★★★ **只测「第 1 轮改过的」+ 它们的下游** | 明显变少 |
| ★ 第 3 轮 | ★★ 只冒烟（能跑通 + 没有内部标记泄漏） | 很少 |

```
★★★★★ **停止条件现在就写死：一轮新发现 < 3 条 → 本版测试结束，发版。**
★ 不写死的后果：★★ 为了「再保险一点」无限加轮，★★★ 而边际发现已经接近 0 —— 纯耗人。
★★ 同理：**第 2 轮不要重跑全量**。★★★ 没被改动、也不在下游的 skill，重跑一遍只是重复确认。
```

### 3.2.4 ★★ 第四件：**同一轮内，一个 skill 只许一个人写**

```
★ 两个人同一轮改同一个 skill → ★★ 测出来的问题**归因不了**（不知道是谁那一改造成的），
   ★★★ 而且容易互相覆盖 → 直接产生返工。
→ ★ 做法：每轮开始时把 38 个 skill 的**责任人列一张表**，一个萝卜一个坑。
★★ 要跨人改 → 先说一声，改完由**后改的那个人**负责复验。
```

### 3.2.5 ★★★ 第五件：**测试用冻结快照，修复在另一份上**

```
★★★★★ 最常见的返工来源：**边测边改** ——
   ★ 测到一半有人改了文件，★★ 后面那半的结果就不知道是对哪一版测的。
→ ★★★ 做法：冻结时**打一个版本号 + md5**，★ 测试全程只对这一份测；
   ★★ 修复都落到下一版，★★★ 不回头改被测的那一份。
```

## 四、AI 在这里面干什么（★ 以及它干不了什么）

```
★★ 能干的：
  · 跑回归、出报告、列出「哪几条和上一版不一样」
  · 按报告提修改建议（★ 建议，不是直接改）
  · 帮忙生成每个 skill 的固定题初版

★★★★★ **干不了的（这一条必须写清楚，否则会出事）**：
  · ★ AI 自己写的检查，**也会错**。
  · ★★ 实证：2026-11-08，一条独立检查线得出「引擎偷看一天、必须改」，
    ★★★ 复核发现是**读代码读错一格**，照它改反而会把引擎改坏。
→ ★★ 所以三条规矩：
  ① ★★★ 测试报告必须写「**本次没测到什么**」—— ★ 不写则报告作废
    （★★ 只报「测到什么」会让人以为「没测到 = 没问题」）
  ② ★★★ 任何「要改核心、要放宽标准」的结论，**必须附数值证据**，不许只凭读代码
  ③ ★ 自证要证明「**它真的起作用了**」，不是「我按了开关」
```
