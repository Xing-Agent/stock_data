## 三、谁改什么（★ 一句话规矩，细表见《130》）

```
★★★★★ **改完之后，同样的问题问系统，它会不会给出不一样的答案？**
   · 会  → **问 Lin**
   · 不会 → **自己改**

★ 「不一样」只看三件：① 选出的**股票**变没变 ② **买/卖/继续拿**的结论变没变
   ③ 原来**能通过**的会不会变成通不过。
★★ 三个都不会 = 表达问题，自己改。★★★ 拿不准 → 当成要问。
```

| 自己改 | 必须问 Lin |
|---|---|
| 话术、示例、解释、提问顺序、表格改列表、K 线怎么显示、错别字 | ★★★ 任何**数字门槛** · 加/删**筛选条件** · **买卖规则** · **排序方式** · **持仓只数** |
| | ★★ 「可能」改成「大概率」这类**对外口径** · 任何写**成绩/收益/胜率**的话 |
| | ★★★★★ 动 **共用边界** |

```
★★ **问的方式**：每组维护一张「要问 Lin 的清单」，★★★ **攒着，每轮固定一次**
  （建议周二）一次性过完 —— ★ 不要零碎打扰，★★ 他还要做策略研究，那部分没人能替。
```

| 类 | 测什么 | 谁 | 多久 |

| ★★★ **三 · 没想到的情况** | ★ 让 AI 针对每张造 **20 个刁钻但合理**的输入：超范围、中途改主意、问别的市场、信息残缺、自相矛盾 | 机器造题 + 人看 | 半天 |


```
★★★★★ **体验不是第四类测试 —— 它属于「改」的阶段**（★ 1109 修订，★★ 原来那样写是自相矛盾的：
  同一张表里一类在冻结前、三类在冻结后）。

| | **AI 体验** | **AI 测试（上面三类）** |
|---|---|---|
| 产出什么 | ★ 「这一步会让人懵」「这句看不懂」 | ★ 「破了边界」「答错」「泄漏内部标记」 |
| 修法是改什么 | ★★★ **改流程、改措辞** | ★★ 改内容 / 改代码 |
| 关键差别 | ★★★★★ **它会改掉被测的那个东西** | ★★★ 它**不改**被测的东西，只找错 |
| 所以它属于 | ★ **「改」的阶段**（冻结前） | ★ **「验」的阶段**（冻结后） |

  ★ 放后面，它一说「顺序该换」，刚跑完的三类**全部作废**。

## 四之二、★★★★★ 第一轮特殊：体验会冒出一大堆，**别按 38 张卡去修**

```
★★★ 第一轮和后面几轮**性质不一样**：
  ★ 后面几轮冒出来的是「**这里做错了**」；
  ★★★ 第一轮冒出来的大部分是「**标准还没定**」—— 同一个措辞问题会在 38 张卡里重复 38 次。
→ ★★ 按「38 张卡 38 个问题」去修，★★★ Lin 会被同一件事问 38 遍。
```

★ 第一轮专用流程（★★ 四步，Lin 只出场一次）：

```
① ★ AI 扮用户走一遍 → 收集所有「懵 / 看不懂 / 别扭」的点
② ★★★ **按原因归类，不按卡归类** ——
   例：「风险说得太软」17 次 ·「没给用户选择」11 次 ·「术语没解释」23 次
③ ★★★★★ 每一类**只问 Lin 一次**：这类该怎么说？→ ★ 他定的就是**标准**
   （★★ 对应《130》B 格那四样）
④ ★★ 各组照标准**批量改**自己那几张
→ ★★★ Lin 被问的次数：**从几十次降到四五次**，一次 30~45 分钟。
```

```
★★ 另外：第一轮**别铺满 38 张** —— ★★★ 措辞问题高度重复，

→ ★★★ 从这 8 张把标准定出来，★★ 再一次性铺到 38 张；
  ★ 第二轮再全量体验 —— 那时剩下的才是真正的「个别问题」。

## 五、三天一轮怎么走

```
第 1 天  ★★ 事前体验（AI 扮用户走一遍，★ 属于「改」不是「测」）→ 定流程 · 各组并行改
第 2 天  ★ 上午继续改 → ★★★★★ **下午冻结**
         ★★ 冻结顺序**从上游到下游**：共用边界 → 两张大卡 → 小卡 → 前后端接线
         ★ 冻结后机器跑：一类冒烟 + 二类边界 + 三类刁钻输入
第 3 天  ★ 上午**分流修**：A 类文字层当场闭环 / B 类代码层进开发队列
         ★★ 下午**只复测修过的那几张** → 发版
→ ★★ 下一轮第 1 天，顺便看上一版的真实使用反馈
```

| 修复分两类 | 谁 | 多久 | ★ 什么时候复验 |
|---|---|---|---|
| ★★ **A · 文字层**：话术、示例、边界提示、格式 | 运营/产品 | 分钟级 | ★★★ 当场改当场验 |
| ★★★ **B · 代码层**：前端呈现、后端接口、字段、路由 | 技术 | 小时~天级 | ★★★★★ **进队列，下一轮验** |

```
★★★ 三条硬的：
① ★★ **冻结之后进来的优化，一律排下一轮** —— 不然永远「上一轮没测完，新版又出来了」。
② ★★★★★ **一轮新发现 < 3 条 → 结束，发版。**（★ 对应边际效应：第 1 轮最多，之后急降）
③ ★★ **B 类修不完不要硬等** —— ★ 这一版照发，★★★ 但版本说明里**写明哪几条已知、下一版修**。
```

```
★ 另外两条防返工的：
· ★★ **同一轮内，一个 skill 只许一个人写**（否则问题归因不了、容易互相覆盖）
· ★★★ **测试对冻结快照测**（版本号 + md5），★ 修复落下一版，**不边测边改**
```
