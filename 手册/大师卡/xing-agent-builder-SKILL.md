## 1  这个 Skill 管什么

帮用户配置 agent:选方法、设参数、定提醒规则。

## 2  什么时候用

【待填】3–5 条用户原话。参考:
- 「帮我盯着这个条件,到了提醒我」
- 【待填】

## 3  不管什么,交给谁

- 替他选方法 → 不管,那是他的决定
- 评价某只股票 → **行情 / K线互动**
- 让他定义全新的规则 → **创建技能**

## 4  这个场景属于哪一档

**搭工具。主动 —— 该给建议就给,而且应该给。**

在一个设置参数的界面上还说「这个判断是你的」,那不是克制,是不帮忙。
**但建议的是「这个参数怎么填」,不是「这只股票该不该买」。**

## 6  这个 Skill 特有的禁令

**一、两套参数值并列,默认原著值。**
原著值 + 我们校准的推荐值,讲清两者的特点和测法,**不推荐哪个**。
默认原著值 —— 用户没主动选之前,不该让他绑在我们自己的规则上。

**二、从原著值切到推荐值,要用户点一下。那一下才是授权。**

**三、绑定之前必须把代价摆出来,不能藏在二级页面。**

七个数 + 可执行率。其中两个的说法已经定了:

> **最大连亏**不能只说「最大连亏 27」,要说
> **「你要准备好连着错 27 次,而且它们会挤在一起来。」**

> **最长水下**不能只说「18 个月」,要说清它包含空仓干等的时间 ——
> 用户的体感是「我账户里的数,18 个月没比之前的最高点更高过」。

**四、不同流派、不同持仓周期的策略,代价数字不放在一起比。**
【待填】决定:并列展示多个策略时,怎么分组。

**五、自研策略严禁套用大师的名字。**
一条我们测出来的规则挂上大师名字,对用户是误导(他以为有几十年验证)。

## 6附  和「创建技能」的分工 —— 两个 Skill,一个入口

**不合并。**理由不是用户认知,是**生命周期不同:**

| | 是什么 | 改了之后影响谁 |
|---|---|---|
| **技能** | **可复用的定义** —— 做一次,到处用 | 所有用它的 agent |
| **agent** | **运行中的实例** —— 挂着标的、有状态、会提醒 | 只有它自己 |

合并等于把「菜谱」和「正在炖的那锅汤」合并。**用户改菜谱的时候,正在炖的那锅怎么办?**
那个问题在合并后的架构里无解。

### 分流判据:他说的里面有没有具体标的

| 用户说 | 判据 | 去哪 |
|---|---|---|
| 「帮我盯一下 **NVDA** 跌破 20 日均线」 | **有标的** → 要的是实例 | **这个 Skill** |
| 「我想做个筛选,找**所有**跌破 20 日均线的」 | **没标的** → 要的是规则 | **创建技能** |

**用户永远不需要知道「agent」和「技能」这两个词。**入口统一,底下分流。

### 引导不在入口,在他重复第三次的时候

**入口不要问「你要建 agent 还是技能」** —— 他不知道,问了也是猜。

```
第一次  「帮我盯 NVDA 跌破 20 日均线」   → 建 agent
第二次  「AMD 也帮我盯一下」             → 再建一个
第三次  「META 也是」
          ↓
系统主动说:「这个条件你用了三次了。要不要存成你自己的技能?
            存了之后下次直接挂标的就行,不用每次重设。」
```

**在他自己已经证明了需求之后再提。**这样他一定懂,因为他刚做了三遍。

### 编辑时必须说出后果

| 场景 | 系统要说什么 |
|---|---|
| 用户改一个**被多个 agent 用着的技能** | **「这会同时影响正在跑的 3 个 agent。改这一个还是全部?」** |
| 用户在 agent 里改的是**条件本身** | 「你改的是技能的定义。只对这个 agent 生效,还是改技能本身?」 |

**那个「菜谱 vs 正在炖的汤」的问题,在这里变成一句用户听得懂的话。**
